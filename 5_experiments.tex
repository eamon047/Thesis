\section{Experiments}
\label{chap:experiments}

\subsection{Experimental Setup}

The experiments use FB15k-237, which contains 14,541 entities and 237
relations. Its training, validation, and test sets contain 272,115, 17,535,
and 20,466 triples, respectively. We consider two KGE model families, RotatE
and TransE. They provide two different model settings for checking whether the
observed relation-level patterns are specific to one embedding model.

For each model family, we use the training configuration selected through the
hyperparameter optimization in the original study
\citep{zhu2024predictive}. One run trained with this configuration is fixed as
the reference model, and additional models are trained with the same
configuration and different random seeds. Let \(H_0\) be the filtered Hits@10
of the reference model and \(H_i\) the filtered Hits@10 of a candidate model. A
candidate is included in the comparable model set when
\begin{align}
    |H_i-H_0| < \epsilon,
    \qquad \epsilon=0.001.
\end{align}
This process is repeated until the model outputs required for the multiplicity
analysis have been collected. Figure~\ref{fig:experimental-workflow} summarizes
this procedure. The performance condition keeps the comparison focused on
models with similar aggregate link-prediction performance, while the different
random seeds allow their query-level decisions to vary. The reference run is
fixed before the relation-level analysis and provides an anchor for defining
this performance neighborhood. The aim is to compare query-level decisions
within that neighborhood, rather than to estimate the best attainable
performance of either model family.

All link-prediction results are evaluated under the filtered setting, and
aggregate performance is reported using Hits@10. For each relation,
we report the relation-level Hits@10, ambiguity(\(\alpha\)), and 
discrepancy(\(\delta\)) defined in Chapter~\ref{chap:framework}. The main 
figures and grouped comparisons retain relations with at least ten test triples
(\(\texttt{test\_support}\geq 10\)); relations below this threshold are not
used in the displayed comparisons.

\subsection{Mapping Type Analysis}
\label{sec:mapping_type_analysis}

Mapping type is the first relation-level structural factor considered in this
chapter. As defined in Chapter~\ref{chap:framework}, it categorizes a relation
according to whether its head side and tail side behave as one or many in the
training graph. This factor is closely tied to the number of plausible entities
that may answer a prediction query. For this reason, it provides a direct way
to examine whether relation-level predictive multiplicity is connected to
graph structure.

\subsubsection{Motivation for Side-Aware Analysis}

For a relation \(r\), tail prediction asks \((h,r,?)\), while head prediction
asks \((?,r,t)\). In the usual link-prediction evaluation, both query types are
part of the same relation-level result. A combined relation-level view therefore
computes one set of metrics for each relation after merging head-prediction and
tail-prediction queries.

This combined view is not fully aligned with how mapping type is defined.
Mapping type assigns the one-or-many property to a specific side of a relation.
For a \(1\)-\(N\) relation, the structurally many side appears in tail
prediction \((h,r,?)\): after the head entity and relation are fixed, multiple
tail entities may be plausible. The same relation does not have the same
structure on the head-prediction side \((?,r,t)\). Conversely, for an
\(M\)-\(1\) relation, the many side appears in head prediction. Therefore,
merging head and tail queries mixes the side where the mapping structure creates
more candidate ambiguity with the opposite side of the same relation.

For this reason, a combined relation-level metric can obscure the pattern that
the mapping type is meant to capture. The main analysis separates head-side and
tail-side prediction so that each metric is compared with the corresponding
side of the relation structure. The combined relation-level view is kept as
appendix-level diagnostic material, and the side-aware results are used as the
main evidence in this section.

\subsubsection{RotatE Results}

Figures~\ref{fig:mapping-rotate-tail} and~\ref{fig:mapping-rotate-head} show
the RotatE results after separating tail prediction and head prediction. Each
figure groups relations by mapping type and reports relation-level Hits@10,
ambiguity \(\alpha\), and discrepancy \(\delta\). Hits@10 gives the
relation-level predictive performance, while \(\alpha\) and \(\delta\) are the
two multiplicity measures used in this chapter.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.86\textwidth]{figures/chap5/mapping_type_RotatE_tail.pdf}
    \caption{RotatE mapping-type results for tail prediction under
    \(\texttt{test\_support}\geq 10\).}
    \label{fig:mapping-rotate-tail}
\end{figure}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.86\textwidth]{figures/chap5/mapping_type_RotatE_head.pdf}
    \caption{RotatE mapping-type results for head prediction under
    \(\texttt{test\_support}\geq 10\).}
    \label{fig:mapping-rotate-head}
\end{figure}

In tail prediction, the \(1\)-\(N\) group has lower Hits@10 and higher
\(\alpha\) and \(\delta\) than the \(M\)-\(1\) group. This matches the
direction of the mapping type: in a \(1\)-\(N\) relation, the tail side is the
many side. The lower Hits@10 indicates that this side is harder to predict,
and the higher \(\alpha\) and \(\delta\) indicate that comparable RotatE runs
also disagree more often on this side.

In head prediction, the pattern changes direction. The \(M\)-\(1\) group now
has lower Hits@10 and higher multiplicity measures than the \(1\)-\(N\) group.
This is consistent with the fact that the head side is the many side for
\(M\)-\(1\) relations. Thus, for RotatE, the mapping-type pattern is not a
single global ordering of relation types. It depends on which side of the
relation is being predicted.

The agreement between RotatE and TransE suggests that this pattern is not only
a peculiarity of one embedding model. At the same time, the claim remains
limited to the current setting: FB15k-237, the repeated-run protocol described
above, relation-level aggregation, and the \(\texttt{test\_support}\geq 10\)
display threshold. Mapping type is therefore treated as the strongest observed
structural factor in this chapter, but not as a complete explanation of
predictive multiplicity.
